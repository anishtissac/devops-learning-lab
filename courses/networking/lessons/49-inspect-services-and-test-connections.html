Understand the idea

Learning target: Use ss, curl, and TCP probes to compare a local service with a remote connection attempt.

Test from both sides of the service boundary

A local listener check answers whether the service has an eligible socket. A local request tests more of the application path. A remote request adds network routing, controls, and possibly intermediaries. Comparing these tests helps locate the additional boundary that introduced the failure.

Use the intended protocol

A TCP probe asks whether a TCP connection can be made. curl tests a higher-level request. An arbitrary TCP success does not validate TLS identity or the application operation. Keep the requested name, address family, path, and credentials aligned with the real workload when reproducing it.

Interpret listener output in context

ss -lnt requests listening TCP sockets using numeric endpoints. Adding -p can show owning processes when permissions allow. Established connections require another view. Read the bind address as well as the port, and run the command in the relevant namespace. Missing process information is not proof that no process owns the socket.

Practical troubleshooting

Symptom

A process exists, but no intended listener appears.

Evidence that narrows the cause

Check startup logs, bind conflicts, effective configuration, and namespace.

Next action and verification

Repair the service startup or bind problem before opening unrelated network rules.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
