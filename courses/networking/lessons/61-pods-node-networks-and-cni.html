Understand the idea

Learning target: Follow Pod-to-Pod and Pod-to-external traffic and understand the role of a network plugin.

A Pod normally shares one network context

Containers in a Pod ordinarily share its network namespace and can communicate through Pod-local loopback. The Pod has its own network identity under the cluster design. Pods are not simply independent host listeners, and a process bound to Pod loopback may be unavailable through the Pod IP.

The network plugin supplies concrete connectivity

CNI-related integration configures container network attachments in many clusters. Plugins can implement routing, overlays, and policy differently. An overlay can carry an inner packet inside another packet; the resulting overhead matters for effective MTU. Do not assume every cluster has one universal bridge or packet path.

Read Pod, node, and external paths separately

A same-node Pod exchange, a cross-node exchange, and Pod egress can cross different boundaries. Node routes, plugin state, underlay reachability, policy, and optional translation can all be relevant. Start from the source Pod's actual namespace and destination rather than using a node-only test as a substitute.

Practical troubleshooting

Symptom

Only cross-node traffic fails.

Evidence that narrows the cause

Compare plugin state, underlay routes, encapsulation rules, policy, and packet-size effects.

Next action and verification

Fix the additional failing path rather than changing every Pod application.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
