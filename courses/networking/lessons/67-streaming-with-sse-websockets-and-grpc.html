Understand the idea

Learning target: Compare short requests with long-lived connections and understand the role of intermediaries.

Streaming changes when useful data arrives

Instead of waiting for one completed response, an application can consume incremental events or messages. Server-Sent Events carries server-to-client text events using the event-stream format. WebSocket supports two-way framed communication after its opening negotiation. gRPC supports unary and streaming RPC patterns. These mechanisms are related use cases, not interchangeable wire protocols.

Intermediaries can change the observed behaviour

A proxy can buffer data before forwarding it or close a connection after a configured idle interval. The upstream application may produce events correctly while the browser sees delayed batches. A connection that carries a short response successfully may still fail during a long stream.

Measure first event and gaps

Distinguish time to headers, time to first useful event, gaps between events, and total duration. An idle timeout concerns an interval without the traffic that resets its timer; it is not necessarily a cap on whole request lifetime. Heartbeats and timeout choices need to match the protocol and intermediary behaviour.

Practical troubleshooting

Symptom

The stream arrives all at once after a long pause.

Evidence that narrows the cause

Compare upstream event timestamps with proxy and client delivery timestamps.

Next action and verification

Inspect buffering and flush behaviour at the stage that batches the data.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
