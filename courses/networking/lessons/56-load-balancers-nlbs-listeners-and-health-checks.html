Understand the idea

Learning target: Separate the user connection from backend traffic and understand what a healthy check actually proves.

Separate the public listener from the backend

A load balancer can expose a client-facing address and port while reaching backends on different addresses, ports, or protocols. Depending on the product and mode, traffic can be terminated, proxied, or forwarded with different source preservation. Draw the actual behaviour rather than assuming every load balancer rewrites addresses in the same way.

A health check is a specific probe

It has its own source context, protocol, port, path, timing, and success criteria. A successful health check proves that its configured test passed at that time. It may not test the public listener, the real Host header, authentication, a slow operation, or every dependency used by users.

Trace both eligible target selection and traffic

A registered backend can be excluded because of health or policy. A healthy target can still be unreachable from the real forwarding path. Inspect listener configuration, backend selection, routes, access rules, host bind, and application logs with one request timeline.

Practical troubleshooting

Symptom

All backends are healthy but the public endpoint fails TLS.

Evidence that narrows the cause

The failure occurs before the backend health result answers the question.

Next action and verification

Inspect client-facing TLS configuration and the requested service identity.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
