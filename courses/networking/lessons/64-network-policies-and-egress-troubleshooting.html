Understand the idea

Learning target: Check permitted traffic, DNS access, external dependencies, and the path back to a Pod.

Policy applies to selected workloads and directions

Standard Kubernetes NetworkPolicy describes permitted network communication for selected Pods. Enforcement requires a networking implementation that supports the policy. A policy object in the API without the corresponding enforcement support does not establish a working security boundary.

Policies combine as permissions

For an isolated direction, permitted traffic is the union of relevant policy allows. A source egress policy and destination ingress policy can both matter to one connection. Policy order is not the same as a first-match firewall rule list. Namespace and Pod selectors must be read in their actual structural context.

DNS and dependencies need their own paths

Allowing an application target does not necessarily allow lookup to the resolver it uses. External services, proxies, and data stores can require separate egress. NAT and implementation details can affect the addresses seen by policy enforcement. Verify the actual plugin behaviour and observation point when an address-based rule is surprising.

Practical troubleshooting

Symptom

Direct IP access works but a name-based request fails after policy changes.

Evidence that narrows the cause

Inspect resolver egress and the application lookup path.

Next action and verification

Permit the required DNS exchange according to the actual resolver design and least required policy.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
