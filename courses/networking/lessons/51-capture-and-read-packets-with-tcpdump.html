Understand the idea

Learning target: Choose an interface and filter, then identify handshakes, retries, resets, and missing responses.

A capture is evidence from one observation point

tcpdump records packets visible to a selected interface and capture mechanism. Choose the interface, protocol, host, port, and time window relevant to the question. Seeing nothing may mean the wrong interface or filter rather than no traffic anywhere. Captures can also be incomplete because of loss, offload, or permissions.

Start with headers and a bounded question

Look for SYN, SYN + ACK, ACK, resets, retransmissions, and response direction. A client-side repeated SYN without a reply narrows the problem but does not identify which remote boundary dropped it. Compare a server-side capture when appropriate. Encrypted payloads generally remain encrypted; a capture is not automatically a view of HTTP content.

Explain the limits of the observation

One capture does not prove what happened before or after its location. Record timestamp, interface, filter, and direction. Capture only the traffic needed for the investigation, since real packets can contain sensitive data. A small local demonstration is enough to learn the header-reading method.

Work through one example

Client capture shows repeated SYNs; server capture sees none.

  1. Confirm that both captures cover the same time, address family, and tuple.
  2. If the observations are accurate, the loss is between those observation points.
  3. Inspect the intervening path rather than assuming the server application rejected data it never received.

What to inspect

The packet count bounds a successful capture, but it can wait if no matching traffic appears. Stop with Ctrl+C when finished.

Practical troubleshooting

Symptom

The capture is empty while the application reports an attempt.

Evidence that narrows the cause

Check namespace, interface, tuple, IPv4/IPv6 selection, and whether the application actually sent traffic.

Next action and verification

Fix the observation point before using absence as evidence of a network drop.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
