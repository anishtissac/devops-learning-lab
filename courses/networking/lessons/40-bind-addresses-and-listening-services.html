Understand the idea

Learning target: Compare loopback, a specific local address, and wildcard listeners, including IPv4 and IPv6 context.

Bind chooses a local listening endpoint

A service can bind a specific local address or an address-family wildcard. An IPv4 listener bound to 127.0.0.1 is reachable through loopback in that namespace. A listener on a particular interface address accepts appropriate traffic addressed there. A wildcard IPv4 bind, 0.0.0.0, covers eligible local IPv4 addresses.

The bind address is not a client destination recipe

A client should use a reachable service address or name. It should not use 0.0.0.0 as if it were the service's public address. IPv6 wildcard listeners and IPv4-mapped handling depend on socket and operating-system settings, so inspect actual family behaviour instead of assuming one listener covers both families.

Visibility and permission remain separate

An ss listing can show a listener while remote traffic still fails because routing or filtering blocks it. Process ownership information may require appropriate permissions. A different container or namespace can have a different listener table, even on the same physical host.

See the relationships

Work through one example

A development service binds 127.0.0.1:8080.

  1. A same-namespace client can reach it through 127.0.0.1.
  2. A request to the host's 10.0.0.10:8080 does not match this loopback-only bind.
  3. Use the intended exposure configuration; a wildcard bind changes eligibility but does not itself permit every network path.
