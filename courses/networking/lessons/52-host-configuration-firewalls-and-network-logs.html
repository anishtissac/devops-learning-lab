Understand the idea

Learning target: Understand persistent configuration, host filtering, connection tracking, and safe diagnosis before changes.

Effective configuration may have several owners

Linux networking can be managed by distribution services, cloud-init, runtime tools, and application startup. A temporary ip command changes kernel state but may not survive reboot or a manager reconciliation. Identify the active configuration owner before deciding how a persistent correction should be made.

Host filtering is another boundary

A service listener and cloud access rule can both be correct while host filtering blocks traffic. nftables, firewalld, or other tooling may manage the effective policy. Inspect the active stack rather than independently editing several layers of tooling. Stateful connection tracking can also affect how later packets are classified.

Use logs to connect cause and time

Service and network-manager logs can show address changes, link transitions, bind failures, or policy reloads. Compare timestamps with the failed workload. Make one justified change at a time, maintain a recovery path, and verify persistence through the intended configuration mechanism. Do not flush live firewall rules as a generic test.

Practical troubleshooting

Symptom

A network fix disappears after reboot.

Evidence that narrows the cause

Compare effective kernel state with persistent configuration and manager logs.

Next action and verification

Correct the intended source of configuration and verify the resulting effective state.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
