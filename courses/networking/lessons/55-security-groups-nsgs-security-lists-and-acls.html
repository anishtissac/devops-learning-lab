Understand the idea

Learning target: Reason about direction, state, rule scope, and return traffic using each provider's model.

Controls have scope, direction, and state

Identify which resource or subnet a control applies to and which endpoint it treats as ingress or egress. A rule should describe source, destination, protocol, and ports as the platform expects them. A service destination port is not the same as the ephemeral port used by a returning client connection.

Stateful and stateless behaviour differ

AWS security groups are stateful, while VPC network ACLs are stateless. OCI NSG and security-list rules can be stateful or stateless according to rule configuration. A stateless policy generally needs explicit permission for the response direction. Mixed controls must all support the actual path; an allow at one boundary cannot override a drop elsewhere.

Inspect the effective policy set

Group associations, subnet controls, host firewall, and additional platform policies can all matter. OCI environments using ZPR also need the relevant ZPR permissions. Do not copy one provider's rule evaluation model into another. Prefer the smallest justified change and test the exact failing flow after it.

See the relationships

Work through one example

A client uses source TCP 51000 to contact server TCP 443.

  1. The request is client:51000 → server:443.
  2. The response is server:443 → client:51000.
  3. A stateless return rule must match the return direction and port context, not simply repeat the request destination rule.

Practical troubleshooting

Symptom

The inbound service rule is correct but replies disappear.

Evidence that narrows the cause

Inspect stateless return rules, client ephemeral ports, and any separate egress control.

Next action and verification

Correct the narrow return-path rule in the proper policy scope.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
