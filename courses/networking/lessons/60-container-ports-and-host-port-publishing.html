Container ports and host port publishing

Distinguish listening inside a container from exposing a port on the host.

Understand the idea

Learning target: Distinguish listening inside a container from exposing a port on the host.

A container listener is not automatically a host listener

An application can listen on TCP 80 inside its own namespace while the host has no corresponding public port. Runtime port publishing supplies a supported mapping or forwarding path from a host endpoint to the container service. The exact implementation depends on runtime, mode, and platform.

Read host port and container port in order

In a common Docker mapping, -p 127.0.0.1:8080:80 publishes host loopback port 8080 toward container port 80. A client of the published endpoint uses 8080, while the application inside the container still listens on 80. EXPOSE metadata alone does not publish a host port.

Both binds and policies still matter

An application bound only to its container loopback may not accept traffic delivered to the container interface. The host publishing address also controls eligibility. Runtime and network modes can change these details; inspect the effective mapping and listener instead of copying a command without understanding its address scopes.

Evidence that narrows the cause

Next action and verification
