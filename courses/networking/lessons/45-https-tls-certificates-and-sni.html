Understand the idea

Learning target: Understand encryption, identity checks, names, trust chains, and the TLS handshake.

TLS protects a connection and authenticates its peer

TLS negotiates cryptographic protection and can validate the server identity through a certificate. HTTPS combines HTTP semantics with TLS-protected transport. A TCP connection can work while TLS fails because of protocol compatibility, trust, identity, time, or other handshake conditions.

The requested name matters

Server Name Indication lets a client name the intended TLS service when the extension is used. Certificate hostname validation separately checks whether the expected identity is covered by the presented certificate. Connecting directly to an IP can change the identity being checked and the certificate selected by a multi-service endpoint.

Trust, name, and application are separate checks

A certificate chain must be acceptable to the client trust configuration and valid for its time and intended use. Successful TLS does not authenticate a user account or establish HTTP success. Disabling verification can hide the identity problem instead of resolving it. Diagnose the certificate, trust source, and requested name explicitly.

Practical troubleshooting

Symptom

TCP connects but the client reports certificate validation failure.

Evidence that narrows the cause

Inspect expected hostname, presented chain, validity period, client time, and trust configuration.

Next action and verification

Correct the identity or trust configuration; preserve verification in the intended client path.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
