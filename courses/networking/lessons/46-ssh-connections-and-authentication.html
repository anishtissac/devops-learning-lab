Understand the idea

Learning target: Separate a failed network connection from a failed SSH login and understand tunnelling basics.

SSH combines several stages

A client first reaches the SSH service over its configured transport endpoint. The protocol negotiates protection and verifies server identity through host-key handling. User authentication follows. A public-key rejection is therefore different from a connection timeout; it indicates progress to a later part of the interaction.

User keys and host keys have different purposes

The server host key identifies the server to the client. A user authentication key helps the client authenticate an account to the server. Replacing one does not automatically repair a problem with the other. A changed host-key warning deserves identity verification rather than automatic deletion of trust records.

Tunnels add another path

SSH forwarding can carry a connection through the SSH channel to another endpoint. The client-to-SSH-server path and the SSH-server-to-target path are different. A working shell login does not prove the forwarded database or application is reachable from the far side.

Work through one example

A user reaches the SSH server but sees Permission denied.

  1. The connection and protocol progressed far enough to attempt authentication.
  2. Inspect account, offered authentication method, key authorisation, and policy.
  3. Do not diagnose this message as proof that the server port is blocked.

Practical troubleshooting

Symptom

SSH login works but a forwarded application fails.

Evidence that narrows the cause

Test the forwarding configuration and far-side target from the SSH server context.

Next action and verification

Repair the separate application path instead of changing working login keys.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
