Understand the idea

Learning target: Build the mental model for an isolated network stack connected to the host.

A network namespace isolates a network stack

Interfaces, routes, socket port space, and several other network resources belong to a namespace. A container commonly runs in an isolated network namespace. Its localhost therefore refers to that namespace. Several containers can also intentionally share a network context, so inspect the runtime design instead of assuming every process is isolated independently.

Virtual Ethernet pairs connect attachment points

A veth pair has two linked endpoints. Placing them in different namespaces provides a software connection between those contexts. A bridge can connect several host-side attachments at the link layer. Routes and optional translation then provide paths beyond that local virtual network.

The observation context matters

Running ip or ss on the host does not automatically display every container's view. Inspect from the relevant namespace or runtime-supported context. A route, listener, or localhost result observed in one stack can be perfectly correct and irrelevant to a request originating in another.

See the relationships

Work through one example

A bridged container sends to an external service.

  1. The container selects its namespace route.
  2. Its interface sends through a veth relationship toward the host bridge and routing path.
  3. The host or platform provides the configured onward forwarding and optional translation. Each boundary has its own evidence.

Practical troubleshooting

Symptom

Host access works but the container cannot connect.

Evidence that narrows the cause

Compare namespace DNS, routes, virtual links, forwarding, and egress controls.

Next action and verification

Locate the failing boundary from inside the actual workload network context.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
