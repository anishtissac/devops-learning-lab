Understand the idea

Learning target: Present an address plan, request-path diagram, troubleshooting record, and a justified corrective action.

Design from requirements, not a collection of icons

Use a web/API entry point, private application backends, a private database, and an external model dependency. State who must reach each service, expected scale, address-family needs, and failure assumptions. Choose a nonoverlapping parent allocation and child ranges with sufficient platform-adjusted capacity and growth space.

Produce an explicit connection inventory

For each connection, record the initiating component, resolver context, destination name and address class, protocol, port, route target, translation or termination, and required policy. Draw the response route as well. Separate user-to-entry, entry-to-application, application-to-database, and application-to-model connections. A simple four-box architecture without these relationships is not enough to explain the actual path.

Inject one failure at a time

Use the browser models or an isolated lab to test a wrong prefix, absent endpoint, blocked return path, wrong certificate name, and excessive stream idle gap. Predict the symptom and discriminating evidence before revealing the result. Keep a working baseline so each failure teaches one boundary instead of an uncontrolled mixture.

Present evidence and verification

Your final deliverables are an address-plan table, labelled traffic diagram, connection inventory, five short incident records, and a verification matrix. Explain why each correction fits the evidence and how the original operation was retested. Include what remains unproven. A defensible explanation is more valuable than claiming that a single successful ping proves the whole architecture.

Work through one example

Use 10.40.0.0/16 as a fictional parent allocation.

  1. Allocate aligned supported child subnets for entry, application, and data functions, calculating capacity under the chosen provider rules.
  2. Expose only the intended entry; document the separate internal and outbound dependency connections.
  3. Inject one routing, one endpoint, and one application-identity failure, then record the evidence and original-request verification for each.
Explain the result: What evidence would demonstrate the full design works? Write your reasoning before opening the answer in the review section.

Change one condition in the path

Turn one condition off and predict the failure. Restore it before testing another condition. Explain why a later healthy component cannot repair the earlier failed requirement.

Practical troubleshooting

Symptom

The design document cannot explain which component initiates a dependency connection.

Evidence that narrows the cause

Missing direction and tuple information makes routing and policy review ambiguous.

Next action and verification

Complete the connection inventory before changing network controls or provisioning another component.

Retest the original operation from the same source context. A successful test of a different endpoint or protocol does not establish that this symptom is resolved.
